mini-vLLM

A from-scratch LLM inference engine. It builds the two systems ideas behind vLLM: continuous batching and a paged KV-cache. It serves an OpenAI-compatible API, and it is checked token for token against Hugging Face transformers.

How it works

Continuous batching

Standard batching waits for a full batch, then releases the whole batch when the slowest sequence finishes. That wastes GPU time whenever sequences differ in length. Continuous batching runs a decode step every tick. New sequences join, and finished ones leave, without stalling the rest. The scheduler decides at each step which sequences run, which wait, and which get preempted under memory pressure. A preempted sequence has its blocks freed, and it is re-prefilled from its prompt and the tokens generated so far when it is admitted again.

Paged KV-cache

The key and value tensors that every attention layer accumulates grow with sequence length. A contiguous buffer per sequence fragments memory and caps the batch size. The paged cache works like virtual memory in an operating system: a fixed pool of physical blocks, each holding a set number of token slots, and a block table per sequence that maps positions to blocks. Sequences of very different lengths share one pool without fragmentation. On CUDA, a custom Triton kernel does the paged attention.

The pieces

  1. API layer. POST /v1/completions in FastAPI, with streaming.
  2. AsyncLLMEngine. One background task steps the engine and sends tokens to each request.
  3. LLMEngine. A scheduler that admits and preempts at every step, and a block manager that owns the pool of physical blocks.
  4. Runner. A dense KV cache for CPU and tests, or the paged runner with the Triton kernel for Llama models on CUDA.
  5. Model and weights. TinyLlama-1.1B and GPT-2.

Correctness

Decoding is checked token for token against Hugging Face transformers. For quantization, the check is a calibrated error bound. All 50 tests pass on the GPU, with none skipped. On a CPU, 39 pass and 11 are skipped, because the Triton kernel and the real-model paged decode need CUDA.

What these numbers do not show

  • All results come from one GPU and one small model, TinyLlama-1.1B.
  • The decode path still loops over the model's 22 layers in Python, and prefill still uses the dense Hugging Face forward pass. Neither is profiled yet.
  • Where the speed-up from the last round of changes comes from has not been measured one change at a time.
  • The first run in a fresh process is much slower than the rest, so the benchmark scripts do an untimed warm-up first.

      Stream from your own server

      The engine needs a GPU (or a CPU with GPT-2), so this page cannot run the model itself. Start the server on your machine, connect, and send several requests at once to watch continuous batching: each request streams on its own lane, with its own time to first token.

      Start the server 
      pip install -e .
MINI_VLLM_MODEL=gpt2 MINI_VLLM_DEVICE=cpu \
MINI_VLLM_CORS_ORIGINS=https://shlokkvaishnav.github.io \
uvicorn mini_vllm.api.server:app --port 8000

      MINI_VLLM_CORS_ORIGINS lets this page call the server. Your browser can ask for permission to reach a local address. Leave out the GPT-2 settings to serve TinyLlama on a GPU.
